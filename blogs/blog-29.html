FIDO2 USB HID to NFC hardware proxy

DATE

Java Cards are really cool, and I guarantee you, the reader, have at least one, probably more in your posession. Bank cards, SIM cards, ePassports are all secretly microcontrollers running Java VMs, and the only difference is in the contact specification, (Dual Contact+NFC, Contact only or RFID only) and deployed applications (referred to as applets). Given their mass proliferation they've been fairly well developed and are very secure environments, and can take on the role of a security token in many contexts. There's several applets available for FIDO2 usage, however many OSs and browsers have fairly crap support for NFC FIDO2 tokens. It can also mean you cant do things like decrypt LUKS encrypted volumes with NFC security tokens. Some people have developed little services that can run on a linux host which present a virtual hid device to the user, then proxy all the data to an NFC reader but given these are userspace applications you can't use them for disk encryption and first login, and they need installing and setting up on every system you connect them to. I decided to try and do something similar but in hardware, essentially a USB NFC reader that presents as a USBHID FIDO2 device so it has wider compatibility. As a bonus i can engineer it to suit my laptop better, but making a nice slim TypeC part that hugs the lapptop so it can remain plugged in the whole time.

Getting started

I decided to spice things up and try a new framework that I hadn't before, so after some googling to figure out what options were out there I settled on the embassy rust framework and the CH32V203 microcontroller. After getting the basic framework workign and blinking a ws2812 I needed to select an NFC chip, I didn't really want to have to write the full driver stack from scratch, but needed full APDU support, so the only driver left was this one for the ST25R95, an NFC IC that's definitely on it's way out but is still available from the usual suspects and i'm not making a commercial product out of this so I don't think it's anything to worry about. Mikroe even have a devkit for it that I could just buy to get started, so I soldered them both to some perfboard and wired it up.

Getting debug data out of this setup is moderately tedious, so I had the bright idea to start with a USB composite device that exposed both a hid device and a serial port, then I can print debugging information through the serial port. Using this guide I modified it for the ch32. starting with the CDC only example, it took quite a bit of screing around to get something working, fiddling with types, drivers and definitions to account for the differences between the rp2040 hal and ch32 hal and then data would only appear in cu when i unplugged the device which was really strange. Turned out cu will not present a new line to the host until it sees a carriage return or the device pipe fails when it's disconnected. Turns out if you use b"string" you can just treat that as a byte array so I could print debug strings really easily. at this state the serial printing was blocking, so if I wasn't connected it wouldn't run the rest of the program. This was solved by using the embassy pipe mechanic. One minor gripe i continue to have with rust is everything is so poorly documented. 99% of how i find out how to do things is by looking at other peopoe's code then smacking my head against the error messages until it works. The pipe seems like a useful construct to use for later in this project, it just needed some tweaking to break the CDC part out into its own task, empty when the pipe is read to send the data out and use try_write to fill the pipe up, because the CDC acm task can't send the data out if the serial port isn't connected.

Adding the HID device was naturally a bit more tricky, FIDO2 HID devices have a pretty simple descriptor, but there's a lot more moving parts with HID. The full FIDO2 U2F HID spec can be found here The descriptor has two 64 byte wide reports, one for data in and one for data out. I didn't fully assemble all the required functions at this time, I just implemented the as_bytes accessor and left the rest for the future. Getting the request_handler working properly was tricky too, the example I was copying implemented some of the requesthandler bits but not all of them leaving me very confused as to how to make it work. Github code examples were also not helpful. It turns out it had to be initialised in a static cell like a lot of the rest of the USB stuff to survive being dispatched into tasks. Onvce a basic HID task was running i flashed it and it showed up as a HID device, and the usb serial was working too, but my led was starting to get very interrupted and stuttery. Along the way I found a vibe coded implementation of the CTAPHID protocol but it was very odd, it didn't properly use reports, it just wrote raw data to the endpoints, which I figured out is probably also what i should be doing as the FIDO2 descriptor doesn't actually have any report IDs
